# Сохранённые локальные стенды Mesh

## Новый стенд: mesh целиком в Docker

- Панель для проверки: **http://localhost:55254/panel/nodes/mesh/** (тестовый `admin` / `admin`). Отдельное имя `localhost` не мешает cookie предыдущего стенда на `127.0.0.1`.
- `sharx-mesh-docker-panel`: Go-контроллер внутри панели, preview-сборка `2.13.0-docker-mesh-dev`.
- `sharx-mesh-docker-n1`, `n2`, `n3`: настоящие production-образы worker с Go mesh внутри `node-service`. `n1` — вход, `n2`/`n3` — выходы.
- `sharx-mesh-docker-b1`: production-образ балансировщика с mesh внутри `sharx-balancer`, роль входа/транзита, настоящий HAProxy.
- `n3` принудительно использует userspace WireGuard; остальные — WireGuard ядра. Это только переключатель испытания, обычный Compose выбирает автоматически.
- Начальный etcd — на `n1`/`n2`/`n3`, внутри тех же контейнеров. Отдельного mesh/etcd-контейнера, systemd, SSH и Docker socket нет.
- Сеть `sharx-mesh-docker-net`, `172.30.204.0/24`; отдельная БД `sharx_mesh_docker` в сохранённом тестовом PostgreSQL. Предыдущие БД и девять нод не изменяются.
- Состояние каждого участника — в его именованном томе `sharx-mesh-docker-<имя>-data`, каталог `/app/data/mesh`. Том панели `sharx-mesh-docker-panel-state` содержит CA и журналы контроллера.

У участников нет опубликованных API-портов на компьютере; тестовый адрес панели опубликован только на loopback. Production Compose использует host networking. В стенде каждый контейнер имеет собственный изолированный сетевой namespace, имитируя отдельный сервер; приложение и его WireGuard работают в одном namespace. Используются `NET_ADMIN`/`NET_RAW` и TUN, без `privileged`.

Для повторения полной проверки из корня репозитория:

```sh
python3 mesh/test/docker_e2e.py
```

Скрипт рассчитан **только на этот выделенный стенд** и его фиксированные имена. Он пересоздаёт его worker/balancer-контейнеры, сохраняя именованные тома, и задаёт новый случайный тестовый pairing secret через память, окружение Docker и тестовую БД. Значение секрета не выводится и не записывается в репозиторий. Старый стенд не затрагивается.

Проверяются: выключенный по умолчанию mesh, JWT, подключение через API, реальный WireGuard kernel/userspace, etcd с mTLS, HAProxy с backend по overlay, потеря канала с переходом на транзит и восстановлением после health-check, релей и возврат хостов, включение/выключение роли etcd на балансировщике через learner, потеря всех процессов etcd, пересоздание worker с тем же ключом и данными, работа при остановленной панели. Инъекции блокировки UDP и остановки etcd восстанавливаются в `finally`.

Проверка данных использует небольшой Go HTTPS fixture на IPv4:9443, а Xray тестового inbound слушает только IPv6 loopback. Fixture запускается тестовой обёрткой перед штатным entrypoint worker и берётся из read-only `/tmp/sharx-docker-https-fixture`. Сам mesh остаётся внутри основного процесса. HAProxy работает по-настоящему; это не проверка всех клиентских протоколов Xray/Telemt.

```sh
docker ps --filter name=sharx-mesh-docker
docker exec sharx-mesh-docker-b1 cat /app/data/mesh/status.json
docker exec sharx-mesh-docker-n3 pgrep -x wireguard-go
docker logs --tail 80 sharx-mesh-docker-panel
```

Стенд и тома оставлены для проверки владельцем. Не выполнять удаление томов или глобальную очистку Docker. Docker-реализация включена в перевыпуск v2.13.0. Стенд изолирован от production; публикация образов не является обновлением рабочего кластера.

## Предыдущий стенд: девять Linux-нод с хостовым агентом

Стенд изолирован от рабочего кластера и существующих серверов. Не удалять: он оставлен для ручной проверки владельцем.

- Панель: **http://127.0.0.1:55253/panel/nodes/mesh/**
- Вход: `admin` / `admin` — только тестовая учётная запись, доступ с loopback.
- Контейнер панели: `sharx-mesh-test-panel`, образ `sharx-mesh-test-panel:local`.
- PostgreSQL: `sharx-mesh-test-db`, база `sharx_mesh_app`, порт `127.0.0.1:55439`.
- Девять Linux-нод: `sharx-mesh-test-n1` … `sharx-mesh-test-n9`, сеть `172.30.203.0/24`, overlay `10.203.0.1` … `.9`.
- `n1` и `n5` — входы; остальные семь нод — выходы. Голосующие etcd: `n1`, `n2`, `n3`.
- На нодах работают настоящие WireGuard-интерфейсы, Go-агенты, etcd с mTLS и Go HTTPS-сервис на 9443 с SNI `mesh.test` для проверки передачи данных.
- Контроллер — часть процесса Go-панели; в образе нет Python. Нодам устанавливаются статические Go-бинарники. Дополнительного mesh-контейнера нет.

Это стенд сетевого механизма: полный worker API SharX, Xray, Telemt и внешний балансировщик на этих Linux-нодах не развёрнуты. Поэтому общий список worker-нод может показывать offline; живость mesh видна на странице Mesh по возрасту агента, матрице связей и кворуму. Реальная передача пакетов проверяется через HTTPS fixture. Не использовать тестовую БД или её доверительную авторизацию в production.

## Управление существующим стендом

```sh
docker ps --filter name=sharx-mesh-test
docker logs --tail 80 sharx-mesh-test-panel
docker exec sharx-mesh-test-n2 journalctl -u sharx-mesh-agent -n 40 --no-pager
docker exec sharx-mesh-test-n2 cat /run/sharx-mesh/status.json
```

Если Docker был остановлен, контейнеры имеют `restart: unless-stopped`. Явный запуск:

```sh
docker start sharx-mesh-test-db sharx-mesh-test-n1 sharx-mesh-test-n2 sharx-mesh-test-n3 sharx-mesh-test-n4 sharx-mesh-test-n5 sharx-mesh-test-n6 sharx-mesh-test-n7 sharx-mesh-test-n8 sharx-mesh-test-n9 sharx-mesh-test-panel
```

Не выполнять `docker compose down -v`, `docker rm` или очистку Docker: часть состояния нод хранится в их файловых системах. Панель хранит CA, SSH identity, журнал релеев и состав нод в томе `sharx-mesh-test-panel-state`. PostgreSQL имеет собственный том. Старые тестовые данные etcd сохранены в каталогах `*.pre-native-bootstrap` / `*.retired-*`; действующие данные находятся в `/var/lib/sharx-mesh-etcd`.

## Повторение сквозных проверок

Из корня репозитория, при работающем стенде:

```sh
python3 mesh/test/e2e.py
```

Скрипт использует только стандартную библиотеку Python как **тестовый клиент**, адрес loopback и фиксированные имена тестовых контейнеров. Проверяет передачу HTTPS, блокирует прямой WireGuard-канал между `n2` и `n3`, проверяет транзит и восстановление, включение DNAT-релея, изменение placement-хостов, конфликт ручной правки и восстановление отключённого хоста с наследуемым портом. Затем временно приостанавливает etcd и проверяет сохранение передачи трафика. Внесённые сетевые блокировки и пауза etcd снимаются в `finally`. Для теста используются хосты/inbound из тестовой базы; не переносить этот скрипт на рабочую панель.

`compose.yaml` и `Dockerfile.node` описывают топологию для нового локального стенда. Существующие контейнеры были созданы напрямую; **не запускать compose поверх них**. Для воспроизведения с нуля необходимы создание тестовой БД `sharx_mesh_app`, регистрация девяти нод, размещение inbound 9443, однократное SSH enrollment и установка HTTPS fixture из `https/main.go`. Рабочие учётные данные и узлы для этого не нужны.

## Проверенные сценарии

- SSH enrollment с подтверждённым host key; изменённый host key отклоняется до передачи пароля.
- Первичная установка нового etcd 3/3 Go-контроллером; mTLS и отказ анонимному клиенту.
- Включение четвёртой ноды через learner, повышение до voter, удаление с сохранением данных; защита минимума трёх voters.
- WireGuard full mesh, автоматический транзит при потере прямого канала, возврат на прямой канал.
- Реальные HTTPS-ответы через overlay и через релей; передача трафика при недоступном etcd.
- Долговечный журнал переключения, отказ перезаписать ручную правку, восстановление исходного порта 0/customized, включая отключённый хост.
- Go-тесты с детектором гонок; полный Go suite с PostgreSQL; сборка интерфейса Next.js.

Ограничения: автоматическую смену публичного IP нельзя воспроизвести сменой адреса у реального хостера в этом локальном стенде; проверены алгоритм трёх различных свежих наблюдений и обновление URL без потери схемы/порта/пути. Независимое исключение участников выбранного пула проверено сервисными тестами с PostgreSQL; полноценный внешний HAProxy-балансировщик здесь не развёрнут. Сертификаты leaf действуют год; автоматическое продление пока не реализовано.

Ничего не выпущено: версия приложения, теги, main и рабочая панель не менялись.

## Интерфейс топологии

На вкладке «Топология сети» доступны карта связей, агентская живость, двунаправленные RTT/loss, активный транзит, таблица etcd (лидер, term/index/applied, размер БД, версия) и HTTPS-доступность выходов. Нажатие на ноду или связь показывает подробности под картой. Серый цвет означает отсутствие свежих данных, жёлтый — асимметрию, красный — отказ, синий пунктир — транзит. Карта ограничена 24 найденными нодами для читаемости; поиск фильтрует по имени и адресам, таблицы сохраняют все строки.

Установка нод, автоматика и настройки вынесены в отдельные вкладки. «Журнал» использует общий `LogExplorer` панели — поиск, уровни, компоненты, временной диапазон, пауза live, раскрытие строки и выгрузка. Источник — последние 50 сохранённых событий контроллера и шаги операций текущего процесса; это не бессрочный архив системных логов. Новые события и шаги имеют Unix timestamp в миллисекундах, чтобы время отображалось в часовом поясе браузера.

Связи на карте имеют движение по доступным направлениям и подсветку при наведении/выборе. Движение отражает доступность канала, а не объём пользовательского трафика. Оно отключается кнопкой и автоматически подавляется при `prefers-reduced-motion`. Интерфейс использует выбранный язык для RTT, единиц времени, заголовков etcd и причин переключения. Формы используют Field/ToggleRow конфигуратора ядра и общие чекбоксы панели. Кнопка «?» открывает справку о ролях, маршрутах, etcd, установке, релеях, автоматике и чтении показателей; поля установки и переключатели имеют контекстные пояснения.

Справка mesh приведена к формату остальных разделов: стандартный HelpScene/ScenePlayerBar с пятью шагами и поясняющие абзацы под ним. Шаг отказа помечает недоступной именно связь, а не здоровые конечные ноды. В карточках нод вход/выход из etcd и удаление агента представлены общими IconButton с tooltip; защиты минимального кворума и подтверждения сохранены.

Карта повторяет радиальную геометрию Remna: входы слева, выходы по дуге, прямые связи и круглые узлы. Если роль одна, используется полная окружность. Серое кольцо — участник etcd, пульсирующее жёлтое — лидер, оранжевая точка — включённый релей. Полные имена и адреса доступны при выборе и в подсказке узла.

При расширении с четырёх до девяти реальных нод обнаружена и исправлена загрузка агента при существующем etcd: до первого запроса устанавливаются отсутствующие начальные маршруты, существующие маршруты транзита сохраняются. Защищено Go-тестом порядка запуска и проверено на новых контейнерах.
