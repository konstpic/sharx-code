## Release v2.11.0

**Release Date:** October 29, 2026

Минорный релиз относительно **v2.10.0**: в XHTTP добавлены `serverMaxHeaderBytes`, `scMinPostsIntervalMs` и `xmux`; исправлены имена полей идентификатора сессии XHTTP; в диалоге версий ядра появился необязательный переключатель на форк Xray-core от SharX.

**Миграция БД:** нет.
**Изменения API:** `GET /panel/api/server/getXrayVersion?source=sharx` возвращает релизы форка (без параметра: официальные релизы, как раньше). Установка версии с суффиксом `-sharx.N` (`/installXray/:version`, `/installXrayOnNodes/:version`) качает ядро из форка. В `xhttpSettings` инбаунда добавлены `serverMaxHeaderBytes`, `scMinPostsIntervalMs`, `xmux`.
**Обновление:** панель и ноды. По умолчанию ничего не меняется: ядро остаётся официальным.

### XHTTP

- Новые поля в форме инбаунда: **Server max header bytes** (только сервер), **Min POST interval (ms)** (число или диапазон, например `10-50`) и блок **xmux** (`maxConcurrency`, `maxConnections`, `cMaxReuseTimes`, `hMaxRequestTimes`, `hMaxReusableSecs`, `hKeepAlivePeriod`). Пустые поля в конфиг не пишутся, существующие инбаунды и их ссылки не меняются.
- `scMinPostsIntervalMs` и `xmux` попадают в параметр `extra` ссылок подписки (vless, trojan, ss, vmess), потому что работают на клиенте. `serverMaxHeaderBytes` в ссылки не попадает. Ядро не позволяет задавать `maxConnections` вместе с `maxConcurrency`. Если задано хоть одно поле xmux, значения по умолчанию для остальных не применяются.
- **Исправление:** панель писала `sessionPlacement` и `sessionKey`, а ядро читает `sessionIDPlacement` и `sessionIDKey`, поэтому размещение идентификатора сессии (заголовок, cookie, query) молча не применялось. Теперь панель пишет имена, которые читает ядро; при чтении принимаются и старые. Ссылки подписки для ранее сохранённых инбаундов переименовывают поля на лету. **Если вы использовали размещение сессии не в `path`, оно начнёт действовать, и клиентам придётся обновить подписку.**
- В список «Uplink HTTP method» добавлен `OPTIONS` (только для ядра-форка, см. ниже). На официальном ядре сервер отвечает на такой запрос как на CORS preflight, и данные не доходят.

### Ядро Xray: необязательный форк SharX

- Dashboard → версии ядра → вкладка Xray: переключатель **Official Xray-core / SharX fork**. По умолчанию выбран официальный. Форк подключается только если админ сам выбрал его версию (тег вида `v26.10.29-sharx.1`); образ, `DockerInit.sh` и обновление по умолчанию остаются на официальном ядре.
- Форк (`konstpic/Xray-core-sharx`) — это официальное ядро плюс исправление: OPTIONS как метод аплинка XHTTP принимается сервером (preflight распознаётся по заголовку `Access-Control-Request-Method`). Клиентам форк не нужен: обычный клиент сам шлёт OPTIONS, если метод указан в `extra`. Исправление предложено в оригинальный репозиторий: XTLS/Xray-core#7290.
- Источник определяется по тегу, закреплённая версия сверяется без суффикса `-sharx`, поэтому повторной установки при каждом запуске нет. Репозиторий форка можно переопределить переменной `SHARX_XRAY_FORK_REPO`. Работает для панели и для нод.
- Скачивание ядра теперь проверяет статус ответа: раньше ошибка 404 записывалась в файл как zip и давала невнятную ошибку распаковки.
- В релиз форка выложены архивы только для linux (amd64, arm64).

### Тесты

- Ядро-форк: тесты по режимам XHTTP (packet-up, stream-up, stream-one, auto), plain и TLS, методам POST, PUT, OPTIONS; без исправления OPTIONS падает во всех режимах. Сквозная проверка: обычный клиент и сервер-форк передают данные, обычный сервер на той же конфигурации нет. Полный `go test ./...` ядра проходит.
- Панель: тесты выбора источника ядра, списка версий форка, скачивания, `extra` ссылок для `scMinPostsIntervalMs` и `xmux`, переименования полей сессии.
