## Release v1.7.12

**Release Date:** September 16, 2026

Патч **v1.7.12** относительно **v1.7.11**: Telemt WEB-режим (MTProto поверх HTTPS/WebSocket) теперь полностью self-contained инбаунд — SharX сам поднимает TLS-терминацию, сам получает Let's Encrypt сертификат и сам проксирует на Telemt. Внешний nginx/HAProxy больше не нужен.

**Миграция БД:** нет. **Конфиг существующих WEB-инбаундов:** нужно один раз пересохранить — поля `vhostPublicAddr`/`listenBind`/`trustedProxyCidrs` убраны из JSON-схемы (см. Operational Notes).

---

### Features

- **Telemt WEB-режим без внешнего прокси** (`node/telemtweb` — новый пакет, `web/service/telemt_config.go`, `node/api/server.go`, `node/configpull/pull.go`, `node/main.go`, `web/service/node.go`, `web/service/telemt_panel.go`)
  - Новый компонент `node/telemtweb.Manager`: общий HTTPS-листенер на ноде/панели (по умолчанию :443), TLS-терминация с автоматическим ACME (TLS-ALPN-01, без занятия порта 80), SNI-роутинг на приватные `transport=web`-листенеры Telemt по нескольким вхостам одновременно
  - `public_addr` для `[[web.vhosts]]` резолвится сама панель через DNS A/AAAA домена — руками вводить IP больше не нужно
  - Приватный bind и `web_trusted_proxy_cidrs` теперь фиксированные внутренние значения (127.0.0.1) — фронт и Telemt всегда на одном хосте, доверять больше некому
  - Пуш конфигурации на воркеры расширен третьим payload'ом (`telemtWeb`) рядом с `telemt`/`amneziawg` — и в push-, и в pull-путях (multi-node и standalone)
  - Изоляция ошибок: если у одного WEB-инбаунда ещё не резолвится домен (DNS не успели прописать), это больше не блокирует пуш конфига для остальных инбаундов на той же ноде — пропускается только сломанный

### UI changes

- Секция "WEB mode" в настройках Telemt-инбаунда упрощена: убраны `vhostPublicAddr`, `listenBind`, `trustedProxyCidrs` и блок с примером nginx-конфига; добавлено опциональное поле `frontPort` (общий порт для всех WEB-инбаундов ноды/панели, по умолчанию 443)

### Operational Notes

- После обновления пересоберите/перезапустите **sharx** и **sharxnode**.
- **Перед включением WEB-режима** направьте DNS A/AAAA запись домена на публичный IP ноды/панели — иначе применение конфига для этого инбаунда завершится ошибкой (остальные инбаунды не пострадают).
- Сертификаты Let's Encrypt кэшируются в `/app/data/telemtweb-certs` (нода) / `<data>/telemtweb-certs` (панель standalone) — это уже персистентные тома, отдельный volume добавлять не нужно.
- Node-контейнер уже запускается с достаточными правами для бинда :443 (без явного `USER` в Dockerfile); если это изменится в будущем — потребуется `CAP_NET_BIND_SERVICE`.
- Существующие WEB-инбаунды с полями `vhostPublicAddr`/`listenBind`/`trustedProxyCidrs` в settings JSON продолжат генерировать TOML (эти поля просто больше не используются), но стоит один раз открыть и пересохранить инбаунд в панели, чтобы подчистить устаревшие поля.

### Test plan

- [ ] `go test ./node/telemtweb/... ./web/service/...` — зелёные (маршрутизация по SNI, применение/остановка листенера, конфликт front-портов, генерация TOML для WEB-режима, DNS-резолвинг замокан)
- [ ] Включить WEB-режим на инбаунде с реальным доменом (DNS уже указывает на ноду) → сертификат выпускается автоматически, `config.toml` содержит корректные `[[server.listeners]]`/`[web]`/`[[web.vhosts]]`/`[[web.vhosts.profiles]]`
- [ ] Два WEB-инбаунда на одной ноде с разными доменами → оба маршрутизируются через один общий front по SNI
- [ ] WEB-инбаунд с ещё не резолвящимся доменом → применение конфига для остальных (не-WEB) инбаундов на той же ноде проходит успешно
- [ ] Два WEB-инбаунда с разными `frontPort` на одной ноде → явная ошибка вместо тихого игнорирования одного из них
