## Release v2.1.1

**Release Date:** September 28, 2026

Релиз **v2.1.1** относительно **v2.1.0**: две правки в обучении конструктора страницы подписки, самолечение миграции 0058 для сломанных бэкапов и запоминание версии ядра Xray/Telemt у standalone-панелей.

**Миграция БД:** да, `0058_bundles.sql` (изменено содержимое, применяется только у тех, у кого 58 ещё не прошла) и новая `0059_repair_balancer_pool_constraints.sql`; применяются автоматически при старте панели.
**Изменения API:** нет.
**Обновление:** образ панели `sharx`; нод и балансировщиков это не касается. У кого `pg_dump` в контейнере панели уже не совпадал по версии с Postgres 16 — переустановите образ, чтобы подтянулся `postgresql16-client`.

---

### Fix: обучение конструктора подписки показывало только Mac-сочетания клавиш

- **Симптом.** В шаге обучения про Undo/Redo и в подсказках самих кнопок «Отменить»/«Повторить» и «Сохранить в хранилище» были только `⌘Z`/`⇧⌘Z`/`⇧⌘S` — пользователи на Windows/Linux не понимали, каким сочетанием пользоваться.
- **Исправлено.** Везде показывается `Ctrl/⌘` вместо голого `⌘`, в конструкторе и в переводах (en/ru).

### Fix: подсказка шага 14 обучения перекрывала окно настроек сетки

- **Симптом.** На шаге «Магнитная сетка» подсказка обучения просила включить сетку через кнопку в тулбаре, но сама вставала прямо под кнопкой — там же, где открывается всплывающее окно настроек сетки, полностью его закрывая.
- **Причина.** Подсказка ставится рядом с подсвеченным элементом; для «широких и невысоких» целей (кнопки тулбара) по умолчанию предпочитается место снизу — туда же, где всплывает попап настроек.
- **Исправлено.** У шага «Магнитная сетка» подсказка теперь принудительно встаёт сбоку, а не снизу.

### Fix: миграция 0058_bundles.sql падала у части standalone-панелей после восстановления из бэкапа

- **Симптом.** При старте панели после восстановления БД через встроенный бэкап/restore (Server → Backup) миграция `0058_bundles.sql` падала: `ERROR: there is no unique constraint matching given keys for referenced table "balancer_pools"`. Панель не поднималась.
- **Причина.** Если в контейнере панели недоступен (или не совпадает по версии с Postgres 16) `pg_dump`, экспорт БД тихо откатывается на собственный экспорт через GORM (`exportDbViaGORM`), который выгружал только колонки — без primary key, unique, foreign key и sequences. После restore такого дампа (импорт дропает всё и накатывает дамп через `psql`) вся схема оставалась без ограничений целостности; это всплывало на первой же миграции с внешним ключом.
- **Исправлено.** 
  - `0058_bundles.sql` теперь сам проверяет и чинит первичный ключ `balancer_pools.id` и внешние ключи `hosts.{inbound,node,pool}_id` перед тем, как их использовать; новая `0059_repair_balancer_pool_constraints.sql` повторяет ту же проверку безусловно — на случай, если восстановление сломанного бэкапа произошло уже после того, как 0058 однажды прошла успешно (и поэтому сама не перезапустится).
  - `exportDbViaGORM` теперь дополнительно выгружает sequences, primary key, unique и foreign key constraints — свежий бэкап через этот путь больше не будет калечить схему.
  - Образ панели теперь ставит `postgresql16-client` из закреплённой версии Alpine (`3.20`), а не `postgresql-client` из вечно «свежего» `alpine:latest` — версия `pg_dump` больше не может разъехаться с Postgres 16 из `docker-compose.yml` и молча свалиться в аварийный экспорт.
- **Проверка.** На тестовой панели дважды воспроизведено ровно repro из бага: сброшен PK `balancer_pools` и каскадно — FK `hosts.pool_id`, миграция помечена невыполненной — сначала как «0058 ещё не проходила» (первое появление бага), затем как «0058 уже применена, ломается позже» (второй сценарий, для которого нужна 0059). В обоих случаях после перезапуска панель поднялась, констрейнты восстановлены, HTTP 200 с панели.

### Fix: standalone-панели не запоминали выбранную вручную версию ядра Xray/Telemt

- **Симптом.** У нод панель помнит версию Xray/Telemt, которую админ поставил вручную, и переустанавливает её, если воркер после обновления образа сообщил другую. У standalone-панели (без мультинод-режима) такого не было: после обновления образа (Watchtower) панель просто оставалась на версии, вшитой в новый образ, хотя раньше версия была явно закреплена через UI.
- **Причина.** `UpdateXray`/`UpdateTelemt` писали выбранную версию только в файлы `xray-version.txt`/`telemt-version.txt` в папке данных — эти файлы никто и никогда не читал.
- **Исправлено.** Версия теперь закрепляется в таблице настроек (`xrayPinnedVersion`/`telemtPinnedVersion`), а не в файлах. При старте панели `ReconcilePinnedCoreVersions` (фоном, не блокируя старт) сверяет закреплённую версию с версией установленного бинарника и при расхождении переустанавливает закреплённую — по той же логике, что и у нод.
- **Проверка.** На тестовой панели вручную закреплена версия Xray, отличная от той, что была в образе; после перезапуска панель определила расхождение (`Xray pinned to v25.9.11 but the installed binary reports 26.9.9`), скачала и поставила закреплённую версию, бинарник на диске подтверждён (`xray -version`). Повторный перезапуск ничего не переустанавливает — переустановка срабатывает только при расхождении.
