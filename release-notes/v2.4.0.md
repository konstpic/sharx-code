## Release v2.4.0

**Release Date:** September 30, 2026

Релиз **v2.4.0** относительно **v2.3.0**: в форме Telemt-инбаунда доступны **все** параметры `config.toml` из справочника Telemt (428 ключей), на Dashboard появился мониторинг доступности Telegram DC, исправлены два дефекта, найденные при проверке.

**Миграция БД:** нет.
**Изменения API:** да. Новые `GET /panel/api/inbounds/telemtParams` (каталог параметров) и `GET /panel/api/inbounds/telemtDcStatus` (статус DC); у агента ноды — `GET /api/v1/telemt-dc-status`. В `settings.telemt` инбаунда добавлены необязательные `params` и `upstreams`.
**Обновление:** обновите панель. Чтобы карточка DC показывала данные с нод, обновите и агент ноды (на старом агенте вместо данных будет пометка «node agent is too old»).

---

### Feature: все параметры Telemt в форме инбаунда

- **Каталог.** Из справочника `CONFIG_PARAMS` Telemt сгенерирован каталог всех ключей (тип, значение по умолчанию, hot-reload, описание, допустимые значения). Генератор — `scripts/gen_telemt_catalog.py`.
- **Форма.** В форме Telemt-инбаунда новый раздел «All Telemt parameters»: секции со счётчиками, поиск по ключу и описанию, фильтр «только заданные», поля по типам (bool, число, строка, список, enum, JSON) и редактор `[[upstreams]]` (direct / SOCKS4 / SOCKS5 / Shadowsocks). В `config.toml` попадают только заданные ключи, остальное остаётся по умолчанию Telemt. Ключи, которыми SharX управляет сам (порты, listeners, API, пользователи), не показываются.
- **Проверка при сохранении.** Значения проверяются по типу и диапазону, а затем настоящим бинарником Telemt («Config error» приходит с сообщением самого Telemt, например `rpc_proxy_req_every must be 0 or within [10, 300]`), поэтому неверное значение нельзя сохранить и сломать процесс на ноде.
- **Версии Telemt.** `web.vhosts.base_path` и `web.debug.sideband` появились только в Telemt 3.5.9. Панель помечает такие ключи и не даёт сохранить их, пока на целевой ноде более старая версия; при отправке на ноду они отфильтровываются.
- **WEB-ссылки.** При заданном `web.vhosts.base_path` ссылка `tg://webproxy` формируется по формату Telemt (`server=host%2Fpath`, secret — base64url от `0x70‖secret`), совпадает с примером из документации.
- **Проверка каталога.** Все 316 доступных для редактирования ключей прогнаны через реальный Telemt 3.5.7 с `config_strict = true`: неизвестными оказались только два ключа выше.

### Feature: доступность Telegram DC

- Карточка «Telegram DC availability (Telemt)» на Dashboard: по каждому Telemt-инбаунду и ноде — DC1–5, медиа-DC и DC203 с состоянием (доступен / деградирует / недоступен) и задержкой; подсказка показывает endpoints, writers и число сессий. Работает и с Middle-End, и без него (по данным upstream), обновляется раз в 15 секунд.
- Данные берутся из `/v1/stats/dcs` и `/v1/runtime/upstream_quality` локального API Telemt. Частичная недоступность запасных endpoint'ов при живых writers считается нормой, а не деградацией.

### Fix

- **Форма инбаунда сбрасывала Middle-End.** У старых Telemt-инбаундов без ключа `useMiddleProxy` форма показывала Middle-End выключенным, хотя реально он работал (по умолчанию включён), и простое пересохранение формы его выключало. Теперь форма показывает фактическое состояние.
- **Telemt на ноде мог остаться остановленным после смены конфига.** Менеджер ноды убивал старый процесс и сразу запускал новый, не дожидаясь освобождения портов; новый падал с «Address in use», и инбаунд оставался мёртвым до следующего применения. Теперь менеджер дожидается завершения старого процесса, а при неожиданном падении перезапускает Telemt с нарастающей паузой (до 5 попыток подряд). Проверено серией из 9 быстрых применений конфига подряд на тестовой ноде.
