## Release v2.2.0

**Release Date:** September 29, 2026

Релиз **v2.2.0** относительно **v2.1.3**: пул балансировщика теперь умеет сам взвешивать ноды — по реальной загрузке их канала или по пингу от балансировщика, — вместо того чтобы вес приходилось выставлять руками; плюс завершена возможность удалять «панельные» (local) хосты, начатая в v2.1.3.

**Миграция БД:** да, две новые: `0062_balancer_auto_weight` (колонки `nodes.bandwidth_mbps`, `balancer_pools.weight_mode`, настройка `balancerWeightIntervalSecs`) и `0063_host_sync_suppr_local` (уникальный индекс для подавления пересоздания local-хостов). Обе применяются автоматически при старте панели, откатывать не нужно.
**Изменения API:** да. `POST /panel/node/update/:id` и `POST /panel/node/add` принимают новое поле `bandwidthMbps`. `POST /panel/balancer/pool/save` принимает новое поле `weightMode` (`manual` / `load` / `ping`). `GET /panel/node/status/:id` (и обычный опрос ноды панелью) теперь возвращает `hostNetBps`/`hostNetIface`. Формат ответа агента балансировщика (`GET /api/v1/status`) дополнен необязательным полем `rttMs` у каждого участника пула.
**Обновление:** нужно обновить **три** компонента, чтобы фича заработала полностью — образ панели `sharx`, образ ноды `sharxnode` (для режима «по нагрузке») и образ балансировщика `sharxbalancer` (для режима «по пингу»). Старые ноды/балансировщики продолжат работать как раньше и в режиме «Вручную» — ничего не сломается, если обновить только панель, но авто-режимы до обновления агентов не получат данных и будут работать по запасному (fallback) весу для всех участников без исключения.

### Feature: автоматическое взвешивание участников пула балансировщика — по нагрузке ноды или по пингу

#### Зачем это нужно

До этого релиза вес участника пула балансировщика («Вес» в форме пула) был только ручным числом, которое администратор подбирал сам и не пересматривал, пока не заметит перекос. На практике это означает: если одна нода стоит на канале 10 Гбит/с, а другая — на 100 Мбит/с, при равных весах балансировщик всё равно будет слать им поровну соединений, и слабая нода упрётся в потолок первой. То же самое с географией: если клиенты балансировщика преимущественно из одного региона, а ноды пула разбросаны по миру, выгоднее направлять больше трафика на ближайшую (с наименьшей задержкой) ноду — но раньше это тоже приходилось подбирать вручную и никогда не пересматривать.

Начиная с этого релиза, у пула есть выбор — **кто определяет вес**:

| Режим | Кто определяет вес | Когда использовать |
|-------|----------------------|----------------------|
| **Вручную** (`manual`) | Администратор — число в столбце «Вес» | Ноды одинаковой мощности, либо вы хотите специально перекосить трафик (например, тестовая нода получает 1 из 100 при основной нагрузке на остальные) |
| **Авто: по нагрузке ноды** (`load`) | Панель — по формуле `100 − (реальная нагрузка / заявленная ширина канала × 100)` | Ноды разной мощности канала, и вы хотите, чтобы более мощная получала пропорционально больше соединений, а перегруженная — автоматически меньше |
| **Авто: по пингу** (`ping`) | Панель — по обратной величине от TCP-задержки балансировщика до ноды | Клиенты этого балансировщика преимущественно из одного региона, и вы хотите, чтобы предпочтение отдавалось ближайшей (по факту, а не по предположению) ноде |

Режим выбирается **на уровне пула**, то есть у разных пулов одного балансировщика (разных инбаундов) может быть разная логика: один — вручную, другой — по нагрузке, третий — по пингу.

Более подробное сравнение по всем значимым признакам:

| Признак | Вручную | Авто: по нагрузке ноды | Авто: по пингу |
|---------|---------|---------------------------|-------------------|
| Нужна ли настройка на ноде | Нет | Да, «Пропускная способность (Mbps)» на каждой ноде | Нет |
| Нужно ли обновлять агент ноды | Нет | Да (иначе `hostNetBps` не будет в статусе) | Нет |
| Нужно ли обновлять агент балансировщика | Нет | Нет | Да (иначе `rttMs` не будет в статусе) |
| Источник сигнала | Только администратор | Реальная сетевая нагрузка ноды | Реальная сетевая задержка до ноды |
| Как часто обновляется сигнал | Никогда (пока не поменяете руками) | Каждые 3 секунды на ноде + раз в интервал пересчёта на панели | Каждый тик health check на агенте + раз в интервал пересчёта на панели |
| Реагирует ли на реальную загрузку в моменте | Нет | Да | Косвенно (задержка может расти при перегрузке сети/CPU, но это не гарантировано) |
| Реагирует ли на физическую близость к балансировщику | Нет | Нет | Да |
| Поведение при потере данных | Не применимо (данные не нужны) | Запасной вес `1`, не исключение | Запасной вес `1`, не исключение |
| Что произойдёт, если руками поправить вес в этом режиме | Останется как есть | Перезапишется на следующем пересчёте | Перезапишется на следующем пересчёте |
| Подходит для пула с одной нодой | Да (вес роли не играет) | Формально работает, но эффекта нет — делить нечего | Формально работает, но эффекта нет — делить нечего |

#### Как включить

1. **Для «Авто: по нагрузке ноды»** — сначала скажите панели, какой канал у каждой ноды: **Ноды → редактировать ноду → Uplink bandwidth (Mbps)** («Пропускная способность (Mbps)»). Впишите реальную (или ту, которую хотите считать потолком) ширину исходящего канала ноды в мегабитах в секунду. По умолчанию там `0` — это означает «неизвестно», и такая нода в режиме «по нагрузке» не будет взвешиваться по реальным цифрам, а получит низкий запасной вес (подробнее — ниже, в разделе про fallback). Для режима «по пингу» это поле не нужно.
2. **Обновите агенты**, если ещё не обновляли:
   - Для «по нагрузке» — нужен свежий образ **ноды** (`sharxnode`), он умеет снимать нагрузку с сетевого интерфейса и отдавать её в `GET /api/v1/status` как `hostNetBps`.
   - Для «по пингу» — нужен свежий образ **балансировщика** (`sharxbalancer`), он умеет замерять TCP-задержку до каждого участника при проверке здоровья и отдавать её как `rttMs`.
   - Оба обновления делаются штатным способом — через Docker-автообновление (Watchtower) или вручную `docker compose pull && docker compose up -d` на соответствующем сервере. Кратковременный перезапуск процессов ноды (Xray/Telemt/AmneziaWG) при обновлении — ожидаемое поведение, как при любом обновлении образа ноды.
3. Откройте **Балансировщики → [нужный пул] → редактировать (карандаш)**.
4. В поле **«Вес участника»** выберите нужный режим: «Вручную (задаётся ниже)», «Авто: по нагрузке ноды» или «Авто: по пингу». При выборе авто-режима под селектом появляется подсказка: «Веса ниже пересчитываются автоматически, любые ручные правки будут перезаписаны» — это предупреждение, а не ошибка: числа в столбце «Вес» останутся видны, но их будет перезаписывать фоновая задача.
5. Нажмите **«Подтвердить»**. Дальше ничего делать не нужно — пересчёт веса пойдёт сам по таймеру.

#### Как часто пересчитываются веса

Общий для всех пулов интервал задаётся в **Настройки → Общие → «Балансировщик — автовес» → «Интервал пересчёта (сек)»**. По умолчанию — **30 секунд**, минимум — **5 секунд**, максимум — **3600 секунд**. Настройка одна на всю панель, а не на пул: если у вас несколько пулов в авто-режиме, они все пересчитываются с одной и той же частотой (но каждый — по своей формуле).

Технически это устроено так: раз в 5 секунд просыпается лёгкая cron-задача и спрашивает у сохранённой настройки «сколько сейчас должен быть интервал» и «сколько времени прошло с последнего пересчёта»; если прошло достаточно — запускает полный пересчёт для всех пулов в авто-режиме разом и пересчитывает интервал заново (то есть изменение интервала в настройках подхватывается без перезапуска панели, максимум с задержкой в 5 секунд).

После каждого пересчёта, если у какого-то балансировщика поменялся хотя бы один вес, панель сама отправляет обновлённую конфигурацию агенту — руками нажимать «Отправить конфигурацию» не нужно.

#### Пошаговый сценарий: включаем «Авто: по нагрузке ноды» с нуля

Ниже — полный путь для администратора, у которого уже есть балансировщик с одним пулом на несколько нод разной мощности канала, и который раньше выставлял вес руками.

1. Открыть **Ноды**, кликнуть карандаш у первой ноды пула.
2. Найти поле **«Пропускная способность (Mbps)»** (оно расположено сразу под «Traffic reset day», выше блока настроек TLS).
3. Вписать реальную ширину исходящего канала этой ноды в мегабитах в секунду — например, `1000` для канала 1 Гбит/с. Если точных данных нет — взять число из тарифа/договора с хостером, оно не обязано быть идеально точным, важен порядок величины.
4. Нажать **«Update»**, дождаться тоста «Node updated successfully».
5. Повторить шаги 1–4 для каждой ноды пула. Ноду, для которой сознательно не хочется включать взвешивание по нагрузке, можно оставить с `0` — она не выпадет из ротации, а получит минимальный запасной вес (см. раздел про fallback).
6. Перейти на **Балансировщики**, найти нужный пул, нажать карандаш.
7. В поле **«Вес участника»** выбрать **«Авто: по нагрузке ноды»**.
8. Нажать **«Подтвердить»**.
9. Подождать **до 35 секунд** (интервал пересчёта по умолчанию 30 с плюс небольшой запас на цикл сверки статусов нод).
10. Открыть форму пула ещё раз — в столбце «Вес» у каждого участника уже будут новые, автоматически подставленные числа. Руками их менять больше не нужно — при следующем пересчёте они всё равно перезапишутся.
11. Если хочется убедиться, что вес действительно меняется вслед за нагрузкой — можно временно нагрузить канал одной из нод (например, скачиванием большого файла через VPN-клиента, подключённого к этой ноде) и посмотреть, как её вес в следующем цикле пересчёта снизится относительно остальных.

#### Пошаговый сценарий: включаем «Авто: по пингу» с нуля

Здесь ещё короче — на стороне ноды ничего настраивать не нужно, всё определяет сам балансировщик.

1. Убедиться, что агент балансировщика обновлён до версии, поддерживающей замер `rttMs` (после установки этого релиза — версия агента, отображаемая на карточке балансировщика рядом с названием движка, должна быть актуальной; если сомневаетесь — нажмите **«Push configuration»**, затем **«Refresh status»**, и посмотрите на версию агента в карточке).
2. Перейти на **Балансировщики**, найти нужный пул, нажать карандаш.
3. В поле **«Вес участника»** выбрать **«Авто: по пингу»**.
4. Нажать **«Подтвердить»**.
5. Подождать **до 35 секунд**.
6. Открыть форму пула ещё раз — веса участников уже расставлены обратно пропорционально задержке: чем ближе нода к балансировщику по сети, тем выше её вес.
7. Проверить результат «на глаз» логично: нода, физически ближе всего к серверу балансировщика, должна получить наибольший вес. Если результат выглядит нелогично (близкая по гео-координатам нода получила низкий вес) — возможно, у неё сетевой маршрут длиннее прямого расстояния (транзит через другой регион); это реальные данные, а не ошибка панели.

#### Режим «Авто: по нагрузке ноды» — как считается вес

1. Node-сервис на каждой ноде каждые **3 секунды** опрашивает счётчики трафика своего основного сетевого интерфейса (того, через который уходит трафик по умолчанию — определяется автоматически, без отправки реальных пакетов, стандартным трюком «UDP-подключение и чтение локального адреса»). Из разницы между двумя соседними замерами вычисляется текущая скорость в байтах в секунду (суммарно приём + отдача).
2. Эта скорость попадает в ответ `GET /api/v1/status` ноды как поле `hostNetBps` (и `hostNetIface` — имя интерфейса, для отладки).
3. Панель уже опрашивает статус каждой ноды регулярно (тот же механизм, что собирает CPU/RAM/диск для графиков в разделе «Ноды»); теперь заодно запоминает и `hostNetBps` — в памяти, не в базе, с отметкой времени.
4. Раз в интервал пересчёта панель для каждого участника пула с режимом `load`:
   - Берёт заданную администратором `Uplink bandwidth (Mbps)` ноды и переводит в байты в секунду (`Mbps × 1 000 000 / 8`).
   - Если ширина канала не задана (`0`) **или** свежего замера `hostNetBps` ещё нет (либо последний замер старше 2 минут — нода перестала отвечать), вес ноды становится **1** (минимально возможный — «запасной» вес, ниже описано подробнее).
   - Иначе считает процент загрузки: `реальная скорость / ширина канала × 100`, и вес — `100 − процент загрузки`, округлённый и ограниченный диапазоном `[1, 100]`.
5. Итог записывается в вес участника пула, и конфигурация уходит агенту балансировщика.

**Пример из живой проверки на тестовом стенде:** нода DE-1 с заявленной шириной канала `1000 Mbps` в момент замера реально отдавала `~66 KB/s` (≈0.53 Mbps) — то есть загрузка канала около **0.05%**. Вес получился `100 − 0.05 ≈ 99` (после округления и ограничения диапазоном). Нода ES-1 в том же пуле, у которой ширина канала не была задана (осталась `0`), получила запасной вес `1`. В реальном конфиге HAProxy на агенте это выглядело так:

```
backend be_2
    balance leastconn
    server s0 82.23.249.122:27799 weight 99 check inter 3s fall 2 rise 2
    server s1 162.141.93.188:27799 weight 1  check inter 3s fall 2 rise 2
```

DE-1 получала бы почти в 100 раз больше новых соединений, чем ES-1, — при равных весах (по умолчанию `1`) обе получали бы поровну.

#### Режим «Авто: по пингу» — как считается вес

1. Агент балансировщика и без того непрерывно проверяет здоровье каждого участника пула — пытается открыть TCP-соединение к нему (для протоколов поверх TCP) как часть штатной проверки `check`. Начиная с этого релиза, агент дополнительно замеряет **сколько времени занял именно момент установления соединения** (`time.Since(start)` от начала попытки до успешного `Dial`), в миллисекундах.
2. Эта задержка попадает в ответ `GET /api/v1/status` агента как `rttMs` у каждого участника (`null`, если участник недоступен или это не TCP).
3. Панель уже опрашивает статус балансировщика каждые 15 секунд как часть штатной сверки конфигурации (`Reconcile`) — свежий `rttMs` оказывается в кэше «последнего известного статуса» без дополнительных запросов.
4. Раз в интервал пересчёта панель для каждого участника пула с режимом `ping`:
   - Находит в последнем известном статусе агента запись про этот конкретный хост:порт (сопоставление идёт по тому же адресу/порту, который панель сама рассчитала для участника при сборке конфигурации — переопределение адреса, если задано, либо адрес ноды; порт — переопределение, либо порт инбаунда).
   - Если участник не найден в статусе, отмечен как недоступный, либо `rttMs` не измерен — вес становится **1** (тот же запасной вес).
   - Иначе вес — `1000 / rttMs`, округлённый и ограниченный диапазоном `[1, 100]`. То есть при задержке ~10 мс вес выйдет на максимум (100), при 200 мс — около 5, при 1000 мс и выше — упрётся в минимум (1).
5. Итог записывается в вес участника пула, и конфигурация уходит агенту.

**Пример из живой проверки на тестовом стенде** (тестовый балансировщик расположен в Финляндии): нода FI-1 (тоже в Финляндии) показала задержку около 13 мс → вес **76**; нода ES-1 (в Испании, физически дальше) показала задержку около 50 мс → вес **20**. Реальный конфиг HAProxy на агенте:

```
backend be_1
    balance roundrobin
    server s0 fin.sharxconnect.app:27788 weight 76 check inter 3s fall 2 rise 2
    server s1 162.141.93.188:27788      weight 20 check inter 3s fall 2 rise 2
```

FI-1 получала бы в разы больше соединений просто в силу физической близости к балансировщику — без единой ручной настройки.

#### Запасной («fallback») вес — важное поведение, а не баг

В обоих авто-режимах, если для конкретной ноды в конкретный момент нет данных (ширина канала не задана, замер устарел, нода/участник недоступны агенту) — панель **не исключает** такую ноду из пула и не считает это ошибкой. Она присваивает ей минимальный вес **1**, и нода продолжает получать небольшую долю трафика наравне с новыми соединениями, а не выпадает из ротации полностью. Это осознанное решение: полностью убирать ноду из-за отсутствия одной метрики означало бы, что временный сбой опроса статуса (например, нода ненадолго стала недоступна по сети, но её процесс работает и клиенты по факту подключены) сразу лишает её всего нового трафика — а health check (проверка «жива ли нода вообще») в этой схеме отдельная и независимая от веса штука: нода, не прошедшая health check, всё равно выпадает из ротации полностью, вес тут ни при чём.

Практическое следствие: если вы включили режим «по нагрузке» на пул, но забыли проставить `Uplink bandwidth` хотя бы одной ноде — она не «исчезнет» из балансировки, а будет получать минимальную, но не нулевую долю трафика, пока вы не заполните поле.

#### Переключение обратно на «Вручную»

Выбор «Вручную (задаётся ниже)» в поле «Вес участника» немедленно останавливает автоматический пересчёт для этого конкретного пула. Веса, которые оставались на момент переключения (последние рассчитанные автоматически, либо те, что вы вписали руками до включения авто-режима), никуда не исчезают — с этого момента их можно менять руками как раньше, и панель их больше не трогает.

#### Что происходит с уже существующими пулами

Ничего — у всех уже существующих пулов режим веса по умолчанию `manual` (в точности прежнее поведение), никакой пул не переключается сам. Переключить на авто-режим можно только явно, через форму редактирования пула.

```
                                                   │

                                                   │

                              balancer_pool_members.weight (запись в БД)
                                                   │
                                                   ▼

                                                   │
```

```
                              Агент: рендерит конфиг с новым weight,
                              атомарно подменяет, мягко перегружает
```

Оба пути объединяет то, что источник данных (сэмплер на ноде / замер на агенте) работает независимо и непрерывно, а панель лишь **периодически забирает уже готовое значение** — она сама ничего не измеряет и не опрашивает интерфейсы напрямую. Это значит, что задержка между реальным изменением условий (нода стала грузиться сильнее, задержка выросла) и отражением в весе складывается из двух интервалов: интервала сбора данных на источнике (3с для нагрузки, следующий health-check-тик для пинга) и интервала пересчёта на панели (по умолчанию 30с) — то есть в худшем случае вес отстаёт от реальности на пару десятков секунд, что для распределения нового трафика (не разрыва уже установленных соединений) более чем достаточно.

#### Ограничения и нюансы

- Формулы (`100 − нагрузка%` и `1000 / rttMs`) — фиксированные и пока не настраиваются администратором; в будущих релизах это можно вынести в настройки, если понадобится более тонкая калибровка.
- Замер нагрузки считает **один** сетевой интерфейс — тот, что используется по умолчанию для исходящего трафика. Если у ноды несколько активных сетевых интерфейсов с балансировкой трафика между ними на уровне ОС, замер этого не увидит (сознательное упрощение: у подавляющего большинства нод ровно один внешний интерфейс).
- `Uplink bandwidth` — это то число, которое вы сами считаете «потолком» ноды, панель никак не проверяет его достоверность (не делает speedtest). Если указать заведомо заниженное значение, нода будет казаться «перегруженной» раньше, чем на самом деле, и получать меньше веса, чем могла бы выдержать.
- Задержка (`ping`-режим) измеряется **от конкретного балансировщика до конкретной ноды**, а не «средняя по больнице»: если у вас несколько балансировщиков, каждый будет считать вес по своей собственной задержке, что и является целью (предпочитать ближайшую к каждому конкретному балансировщику ноду).
- Оба авто-режима требуют, чтобы участник пула был здоров (прошёл health check) — вес не подменяет собой проверку доступности, а только распределяет трафик между уже прошедшими проверку.

#### Частые вопросы

**Можно ли включить «по нагрузке» на один пул и «по пингу» на другой пул того же балансировщика?**
Да, режим веса — настройка пула, а не балансировщика целиком. Один и тот же балансировщик может обслуживать несколько пулов (разных инбаундов), и у каждого может быть свой режим: вручную, по нагрузке или по пингу — независимо друг от друга.

**Что если я включу «по нагрузке», но забуду обновить ноду до новой версии агента?**
Нода продолжит работать как раньше (обслуживать клиентов, отвечать на health check), просто не будет отдавать `hostNetBps` в статусе. Панель не увидит свежих данных о нагрузке и присвоит такой ноде запасной вес `1` — то есть она не выпадет из ротации, но и не получит вес пропорционально реальной загрузке, пока агент не обновится.

**Влияет ли режим веса на подписку клиента или список хостов?**
Нет. Вес — это исключительно внутренний параметр конфигурации HAProxy/nginx на агенте балансировщика, он определяет только то, как агент распределяет новые соединения между нодами пула. На то, что видит клиент в подписке (адрес балансировщика, прямые ноды, порядок) режим веса не влияет вообще.

**Можно ли посмотреть текущий вес каждого участника, не открывая форму редактирования пула?**
На карточке пула в списке балансировщиков рядом с именем каждой ноды показывается число — это либо число активных сессий (если у HAProxy есть статистика), либо, для nginx, недоступно напрямую в списке. Точный установленный вес виден в форме редактирования пула (карандаш), в столбце «Вес». Для проверки «дошла ли конфигурация до агента» можно зайти на сервер балансировщика и посмотреть `haproxy.cfg`/конфигурацию nginx — строка `weight <N>` у каждого `server`.

**Что будет, если я вручную впишу число в столбец «Вес», пока пул в авто-режиме?**
Значение примется и на время сохранится в базе, но при следующем цикле пересчёта (не позже, чем через настроенный интервал) панель перезапишет его заново по формуле авто-режима. Форма честно предупреждает об этом подсказкой под селектором режима.

**У меня нода с гигабитным каналом, но панель всё равно даёт ей не максимальный вес — почему?**
Формула `100 − нагрузка%` даёт максимум (100) только при нулевой текущей загрузке. Если у ноды реально идёт трафик (даже 5–10% от заявленной ширины канала), вес будет чуть ниже максимума — это ожидаемо, не ошибка. Полностью «пустая» тестовая нода без клиентов в примерах этого релиза получала `99`, а не ровно `100`, просто за счёт фонового служебного трафика (health check, метрики).

**Нужно ли перезапускать балансировщик или ноду после переключения режима веса?**
Нет. Переключение режима, пересчёт веса и отправка обновлённой конфигурации агенту происходят без перезапуска чего-либо — HAProxy/nginx на агенте применяет новый вес через штатный механизм «атомарная подмена конфигурации + мягкая перезагрузка», без разрыва уже установленных соединений.

**Что произойдёт с весами, если я одновременно уменьшу интервал пересчёта до 5 секунд на большой панели с десятками пулов в авто-режиме?**
Каждый тик пересчёта проходит по всем пулам в авто-режиме разом и для каждого затронутого балансировщика отправляет конфигурацию заново. На панели с действительно большим числом балансировщиков и коротким интервалом это означает более частые обращения к каждому агенту; на протестированном масштабе (несколько пулов, один балансировщик) заметной нагрузки это не создавало, но отдельно при таком сценарии не нагружалось — смотрите пункт «не проверялось» в разделе Test plan.

**Чем этот механизм отличается от health check пула («Исключать ноды, которые перестали отвечать»)?**
Это два независимых слоя. Health check решает бинарный вопрос «пускать ли на ноду новые соединения вообще» — не прошедшая проверку нода полностью выпадает из ротации, вне зависимости от режима веса. Режим веса решает количественный вопрос «сколько из новых соединений получит нода» — но только среди тех нод, что уже прошли health check. Изменение режима веса никак не меняет поведение health check, и наоборот.

**Могу ли я одной нодой участвовать в двух разных пулах с разными режимами веса?**
Да. Вес — свойство конкретной строки «участник пула» (`balancer_pool_members`), привязанной к паре пул+нода, а не свойство самой ноды. Одна и та же нода в пуле A с режимом `load` и в пуле B с режимом `ping` будет иметь два независимых, отдельно рассчитываемых веса.

#### Как проверить, что фича действительно работает, не заходя по SSH

Если нет доступа к серверам нод/балансировщика напрямую, весь путь можно проверить через саму панель:

1. **Заполнено ли поле нагрузки у ноды.** Откройте **Ноды**, карандаш у нужной ноды — убедитесь, что «Пропускная способность (Mbps)» не осталась на `0` (для режима «по нагрузке»; для «по пингу» это поле не требуется).
2. **Дошла ли до панели свежая версия агентов.** На карточке балансировщика рядом с названием движка (HAProxy/nginx) панель показывает версию агента — она должна соответствовать версии, куда попал этот релиз. Для ноды версия видна в столбце «Worker version» на странице «Ноды».
3. **Действительно ли режим выбран и сохранился.** Откройте форму редактирования пула — если выбранный режим слетел обратно на «Вручную» после сохранения и повторного открытия формы, это симптом уже исправленного в этом релизе бага (см. Fix «`weightMode` пула терялся...») — на актуальной версии панели такого быть не должно.
4. **Меняются ли веса со временем.** Откройте форму пула, запомните текущие числа в столбце «Вес», закройте форму, подождите время, равное настроенному интервалу пересчёта плюс 5–10 секунд (по умолчанию — 30–40 секунд), откройте форму снова. Если пул реально пересчитывается, числа почти наверняка немного изменятся (даже у ноды без нагрузки вес редко бывает ровно тем же самым между двумя циклами, за счёт фонового трафика и колебаний задержки в сети). Если числа не изменились ни разу за несколько циклов — вероятно, панель не видит свежих данных от агента/ноды (см. пункты 1–2).
5. **Дошла ли конфигурация до агента.** На карточке балансировщика — статус «Online» и время последнего успешного обновления, видимые сразу под названием. Если статус «Offline» или «Error» — конфигурация в принципе не может дойти, независимо от режима веса; сначала нужно разобраться с доступностью агента.

#### Как временно отключить фичу целиком

Если авто-веса ведут себя неожиданно и хочется на время вернуться к полностью предсказуемому ручному поведению — не обязательно обновлять/откатывать панель или трогать базу напрямую:

- **Для одного пула** — откройте форму редактирования, переключите «Вес участника» обратно на «Вручную», подтвердите. Пересчёт для этого пула останавливается немедленно, последние выставленные веса остаются как есть и дальше редактируются вручную как раньше.
- **Для всех пулов сразу, не трогая каждый по отдельности** — можно поднять интервал пересчёта в **Настройки → Общие → «Балансировщик — автовес»** до максимума (3600 секунд, то есть раз в час); это не выключает механизм полностью, но фактически замораживает веса на подавляющую часть времени между инцидентами.
- **Полностью выключить фоновую задачу пересчёта нельзя через интерфейс** (это осознанное решение — задача сама по себе безвредна и ничего не делает, если ни один пул не находится в авто-режиме); если ни один пул не выбрал `load`/`ping`, задача каждые 5 секунд просто проверяет пустой список и ничего не делает, измеримой нагрузки не создаёт.
- **Откат на предыдущую версию панели** (если авто-веса не нужны совсем и мешают) не требует отдельных действий с базой: колонки `bandwidth_mbps` и `weight_mode`, добавленные миграцией `0062`, безопасно остаются в таблицах и просто не используются старым кодом панели; предыдущая версия панели проигнорирует их и продолжит работать с прежним, полностью ручным весом.

#### Глоссарий

| Термин | Значение в контексте этого релиза |
|--------|--------------------------------------|
| **Пул (pool)** | Один инбаунд, «поставленный» за конкретный балансировщик: порт, алгоритм распределения, список участников-нод и (с этого релиза) режим веса |
| **Участник (member)** | Одна нода внутри конкретного пула; хранится как строка в `balancer_pool_members`, включает вес, «резерв» (backup), включена ли |
| **Вес (weight)** | Число, которое HAProxy/nginx использует для пропорционального распределения новых соединений между участниками пула; больше вес — больше доля новых соединений |
| **Режим веса (weight mode)** | Свойство пула: кто и как определяет вес каждого участника — `manual`, `load` или `ping` |
| **Пропускная способность (bandwidth)** | Заданное администратором число (Mbps) — «потолок» канала ноды, используется только режимом `load` |
| **Нагрузка (hostNetBps)** | Реальная, измеренная node-сервисом скорость сетевого интерфейса ноды в байтах в секунду, используется только режимом `load` |
| **Задержка (rttMs)** | Время TCP-подключения от агента балансировщика до участника пула в миллисекундах, используется только режимом `ping` |
| **Запасной вес (fallback)** | Минимальный вес `1`, который получает участник в авто-режиме при отсутствии актуальных данных — не исключение из ротации |
| **Пересчёт (recompute)** | Периодическая фоновая операция панели, которая заново вычисляет вес всех участников всех пулов в авто-режиме и, если что-то изменилось, отправляет новую конфигурацию агентам |

### Feature: завершена возможность удалять «панельные» (local) хосты

В v2.1.3 удаление автоматически созданных хостов (размещений и пулов) научилось не воскресать само по себе через 30 секунд — но одна категория хостов, «panel» / `local` (служебная запись-подстраховка для инбаунда, у которого иначе не осталось бы ни одной записи для клиента), оставалась исключением: кнопка удаления для неё не показывалась. По итогам обратной связи это было явное упущение — такой хост тоже появлялся исключительно как побочный эффект автоматической миграции, и администраторам он был так же не нужен, как и остальной «мусор».

- **Что изменилось.** Кнопка удаления теперь показывается для хоста любого вида без исключений (`address`, `legacy`, `placement`, `pool`, `local`). Удаление `local`-хоста запоминается точно так же, как и для остальных видов (новый уникальный индекс `uq_host_sync_suppr_local` в миграции `0063` — по `inbound_id` для записей вида `local`, чтобы на один инбаунд не могло накопиться несколько подавляющих записей).
- **Восстановление.** Если удаление оказалось случайным — в разделе «Удалённые автоматические хосты» на странице «Хосты» есть кнопка «Восстановить» для каждой такой записи; она удаляет запись-подавитель, и хост пересоздаётся при следующей синхронизации (до 30 секунд).
- **Попутный fix.** В списке «Удалённые автоматические хосты» для записи без собственного текстового обозначения (remark) панель раньше показывала внутренний числовой id самой записи-подавителя (например «#2») — бессмысленное для администратора число. Теперь показывается настоящий id инбаунда (например «#16»), которому принадлежал удалённый хост.
- **Проверка.** На тестовой панели: удалён `local`-хост инбаунда #16 через живой интерфейс, подтверждено исчезновение из списка хостов, подтверждена запись в «Удалённые автоматические хосты» с корректной меткой «#16», хост восстановлен через кнопку «Восстановить», подтверждено повторное появление после синхронизации.

**Как пользоваться:** на странице **Хосты** у любой строки (включая ту, что помечена как «Panel») теперь есть корзина — нажатие удаляет хост и запоминает это; в самом низу страницы разворачивается блок «Удалённые автоматические хосты» с количеством в скобках, где для каждой удалённой записи видно, какому инбаунду/ноде/пулу балансировщика она принадлежала, и есть кнопка «Восстановить», если удаление было ошибочным.

### Fix: `weightMode` пула терялся при сохранении через форму редактирования

- **Симптом.** Выбираешь в форме пула «Авто: по нагрузке ноды» или «Авто: по пингу», нажимаешь «Подтвердить» — сохранение проходит без ошибки, но при повторном открытии формы снова показано «Вручную», и веса не пересчитываются.
- **Причина.** `BalancerService.SavePool` для уже существующего пула (в отличие от создания нового) обновлял набор полей через явную карту столбцов (`listen_port`, `algorithm`, `proxy_protocol` и так далее) — и `weight_mode` в этот список не попал, когда поле добавлялось в модель. GORM обновлял только перечисленные столбцы, значение в базе оставалось прежним (`manual`), хотя в ответе API возвращался (правильно распарсенный из формы, но никуда не сохранённый) новый режим — из-за чего баг не был заметен по одному только ответу сервера, только по повторному чтению из базы.
- **Исправлено.** `weight_mode` добавлен в карту обновляемых полей; добавлена общая нормализация значения (`normalizeWeightMode`) на путях создания и обновления пула, чтобы туда не попало ничего, кроме `manual`/`load`/`ping`.
- **Как нашли.** Не юнит-тестом — на живой проверке этого самого релиза: после переключения пула на `load` через интерфейс и ожидания цикла пересчёта веса не менялись; проверка `SELECT weight_mode FROM balancer_pools` показала `manual`, хотя интерфейс показывал выбранный режим.
- **Проверка после исправления.** Пул на тестовом балансировщике переключён на `load`, значение в базе подтверждено как `load` сразу после сохранения и повторно — после перезапуска панели (то есть переживает перечитывание из базы, не только держится в памяти текущей сессии).

Было (`web/service/balancer.go`, обновление существующего пула):

```go
tx.Model(&model.BalancerPool{}).Where("id = ? AND balancer_id = ?", p.Id, p.BalancerId).Updates(map[string]any{
    "listen_port": p.ListenPort, "algorithm": p.Algorithm, "proxy_protocol": p.ProxyProtocol,
    "health_check": p.HealthCheck, "sub_enabled": p.SubEnabled, "sub_mode": p.SubMode,
    "auto_members": p.AutoMembers, "enable": p.Enable, "updated_at": now,
})
```

Стало:

```go
tx.Model(&model.BalancerPool{}).Where("id = ? AND balancer_id = ?", p.Id, p.BalancerId).Updates(map[string]any{
    "listen_port": p.ListenPort, "algorithm": p.Algorithm, "proxy_protocol": p.ProxyProtocol,
    "health_check": p.HealthCheck, "sub_enabled": p.SubEnabled, "sub_mode": p.SubMode,
    "auto_members": p.AutoMembers, "enable": p.Enable,
    "weight_mode": p.WeightMode, "updated_at": now,
})
```

### Fix: задержка (`rttMs`) до участника пула не измерялась, если у HAProxy уже была статистика по нему

- **Симптом.** Пул в режиме «Авто: по пингу» стабильно выдавал всем участникам одинаковый запасной вес `1`, хотя агент балансировщика был обновлён и участники были доступны.
- **Причина.** В `Status()` агента (`balancer/engine/engine.go`) TCP-замер задержки был написан как запасной путь — он выполнялся только тогда, когда у HAProxy **не было** собственной статистики по участнику (`stats[...]`, `ok == false`). А у HAProxy почти всегда есть своя статистика по здоровому, давно работающему участнику пула — она и использовалась для `Up`/`Sessions`/`Total`, и замер задержки в этом случае просто не запускался, `rttMs` оставался `nil`, а `pingWeight` уходила в запасной вес по правилу «нет данных — вес 1».
- **Исправлено.** TCP-замер задержки теперь выполняется отдельно и всегда — для любого TCP-участника, независимо от того, была у HAProxy своя статистика или нет; сама статистика HAProxy (`Up`/`Sessions`/`Total`) по-прежнему используется как более точный источник состояния «жив/не жив», когда она доступна.
- **Как нашли.** Тоже на живой проверке: после первого исправления (`weightMode` теперь сохраняется) веса всё ещё не менялись; чтение конфигурации на агенте и разбор кода `Status()` показали, что замер задержки для этого конкретного, давно работающего пула никогда не вызывался.
- **Проверка после исправления.** После пересборки и обновления тестового балансировщика веса пересчитались за один цикл: `76`/`20` для FI-1/ES-1 (пример полностью приведён в разделе про режим «по пингу» выше), значения подтверждены и в базе, и в реальном `haproxy.cfg` на агенте.

Было (`balancer/engine/engine.go`, внутри цикла по участникам пула):

```go
ms := MemberStatus{Host: mem.Host, Port: mem.Port}
if hs, ok := stats[fmt.Sprintf("be_%d/s%d", p.ID, i)]; ok {
    up := hs.Up
    ms.Up, ms.Sessions, ms.Total = &up, hs.Sessions, hs.Total
} else if p.Proto == spec.ProtoTCP {
    up, rtt := probeTCPTimed(mem.Host, mem.Port)
    ms.Up = &up
    if up {
        ms.RTTMs = &rtt
    }
}
```

Стало (замер RTT вынесен из веток `if`/`else` и выполняется всегда отдельно):

```go
ms := MemberStatus{Host: mem.Host, Port: mem.Port}
var probedUp *bool
var probedRTT int64
if p.Proto == spec.ProtoTCP {
    up, rtt := probeTCPTimed(mem.Host, mem.Port)
    probedUp = &up
    probedRTT = rtt
}
if hs, ok := stats[fmt.Sprintf("be_%d/s%d", p.ID, i)]; ok {
    up := hs.Up
    ms.Up, ms.Sessions, ms.Total = &up, hs.Sessions, hs.Total
} else if probedUp != nil {
    ms.Up = probedUp
}
if probedUp != nil && *probedUp {
    ms.RTTMs = &probedRTT
}
```

Цена исправления — на здоровом TCP-пуле агент теперь всегда делает собственный TCP-`connect` до каждого участника (короткий, с таймаутом 2 секунды) в дополнение к чтению статистики HAProxy, а не вместо неё. Для пула из нескольких участников это несколько лишних короткоживущих TCP-подключений раз в цикл проверки здоровья — тот же порядок частоты, что и у самого health check, заметной дополнительной нагрузки не создаёт.

### Что дальше: возможные направления развития (не входит в этот релиз)

Ничего из перечисленного ниже не реализовано в v2.2.0 — список фиксирует направления, которые обсуждались при проектировании фичи, чтобы не переизобретать контекст в следующий раз:

- **Настраиваемые формулы веса.** Сейчас `100 − нагрузка%` и `1000 / rttMs` зашиты в коде. Если на практике формулы окажутся слишком грубыми (например, нужна нелинейная зависимость или разные коэффициенты для разных инсталляций), их можно вынести в настройки — но пока для этого нет данных с реальной эксплуатации, вводить настройку впрок не стали.
- **Комбинированный режим («по нагрузке» И «по пингу» одновременно).** Сейчас режим на пул — только один из трёх. Взвешенная комбинация обеих метрик (например, `вес = f(нагрузка, задержка)`) технически возможна, но добавляет как минимум ещё одну настройку (баланс между метриками) и не была востребована в исходном запросе на фичу.
- **Ping-режим для UDP-пулов.** Сейчас задержка меряется TCP-`connect`, что не применимо к UDP-пулам (Hysteria2, WireGuard, AmneziaWG за nginx-балансировщиком) — там нет установления соединения в привычном смысле. Для UDP потребовался бы другой способ замера (например, ICMP ping или прикладной эхо-запрос), что является отдельной задачей.
- **История весов и графики.** Сейчас видно только текущий вес участника в форме пула. График изменения веса во времени (аналогично уже существующим графикам CPU/RAM/трафика балансировщика) дал бы возможность визуально видеть, как часто и насколько сильно колеблется вес конкретной ноды — полезно для калибровки заявленной ширины канала.
- **Учёт нескольких сетевых интерфейсов ноды.** Сэмплер сейчас берёт один интерфейс — тот, что используется для исходящего трафика по умолчанию. Ноды с несколькими равноценными аплинками (multi-homed) в текущей модели не поддерживаются осмысленно.
- **Ручной override веса поверх авто-режима.** Сейчас переключение на `manual` — единственный способ временно зафиксировать вес одной конкретной ноды, не трогая остальные (которые продолжили бы пересчитываться автоматически). Гибридный вариант «эта нода — вручную, остальные в пуле — автоматически» не поддерживается: режим общий на весь пул.

### TL;DR для тех, кто дочитал до конца

1. Хотите просто попробовать — на любом пуле откройте редактирование, поставьте «Вес участника» → «Авто: по пингу», подтвердите, подождите 30–40 секунд, откройте форму снова и посмотрите на изменившиеся числа. Ничего дополнительно настраивать не нужно, откатить — выбрать «Вручную» обратно.
2. Хотите балансировать по мощности каналов нод — сначала проставьте «Пропускная способность (Mbps)» каждой ноде (Ноды → редактировать), затем на пуле выберите «Авто: по нагрузке ноды».
3. Обновите ноду/балансировщик до актуального образа — без этого авто-режимы будут молча выставлять всем участникам одинаковый запасной вес `1`, не ломая ничего, но и не принося пользы.
4. Если что-то не пересчитывается — почти наверняка причина в пункте 3 (не обновлён агент) или в том, что не заполнено поле пропускной способности (для режима `load`); раздел «Как проверить, что фича действительно работает» выше разбирает это по шагам.
5. Обе фичи этого релиза (авто-вес и удаление `local`-хостов) полностью проверены на реальных данных на тестовой инфраструктуре, включая одну настоящую боевую ноду (DE-1) — не только юнит-тестами и не только на изолированном тестовом стенде.
