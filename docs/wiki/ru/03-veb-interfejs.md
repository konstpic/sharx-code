# 3. Веб-интерфейс

[← Установка](./02-ustanovka.md) | [Оглавление](./README.md) | [Подключения →](./04-podklyucheniya.md)

## Вход в панель

1. Откройте адрес панели в браузере (по умолчанию `http://сервер:2053`).
2. Введите логин и пароль администратора.
3. При включённой двухфакторной аутентификации (2FA) введите код TOTP или подтвердите через Telegram.

Сессия хранится в зашифрованных cookie — повторный ввод пароля не требуется до истечения сессии или выхода.

## Дашборд

Главная страница показывает:

- **Общий трафик** — загрузка и отдача за период.
- **Онлайн-клиенты** — количество активных подключений.
- **Состояние Xray** — запущен / остановлен / ошибка (в single-node режиме).
- **Состояние нод** — online/offline, Xray на каждой ноде (в multi-node).
- **Графики** — динамика трафика и подключений.

Данные обновляются в реальном времени через WebSocket.

## Публичная страница подписки

Отдельный маршрут `/panel/sub/?id=<subId>` — страница для конечных пользователей без бокового меню панели. Открывается при переходе по ссылке подписки из браузера.

## API Docs

Встроенный просмотрщик REST API (`/panel/api-docs/`) — описание эндпоинтов для автоматизации и интеграций. Полная документация: `web/docs/API.md`.

## DB Inspector

Раздел **Настройки → DB Inspector** (`/panel/db-inspector/`) — просмотр таблиц PostgreSQL для отладки. Не предназначен для повседневной работы.

## Типичный рабочий процесс

```
1. Дашборд          → проверить состояние системы
2. Подключения      → создать/настроить inbound
3. Клиенты           → добавить пользователя, назначить inbound
4. Настройки панели → «Подписка и JSON» → оформить страницу подписки
5. Передать клиенту ссылку подписки
```

При multi-node:

```
1. Настройки → включить Multi-Node
2. Ноды → добавить воркеры
3. Подключения → создать inbound → назначить ноды
4. Хосты → настроить CDN/домены для подписок
5. Клиенты → создать и назначить inbound'ы
6. Настройки панели → «Подписка и JSON» → оформить страницу
```

## Виджет дашборда: доступность DC Telegram (Telemt)

Виджет **Telemt DC** показывает, как каждый запущенный инстанс Telemt (MTProto) достаёт до дата-центров Telegram. Он появляется, только если запущен хотя бы один инбаунд Telemt (на хосте панели в одиночном режиме или на нодах в мультинодовом режиме).

**Как собираются данные.** Браузер опрашивает `GET /panel/api/inbounds/telemtDcStatus` (по умолчанию каждые 15 с; можно выбрать 5/15/30/60 с, выбор запоминается в браузере). Панель обращается к локальному control API каждого инстанса Telemt (`/v1/stats/dcs`, `/v1/runtime/upstream_quality`, `/v1/runtime/me_pool_state`, `/v1/runtime/me_quality`); в мультинодовом режиме это делает агент каждой ноды, а панель опрашивает все ноды параллельно с таймаутом 8 с на ноду. Результат кэшируется на несколько секунд, поэтому несколько открытых дашбордов не умножают нагрузку. Если нода перестала отвечать, до 10 минут показываются её последние известные данные с пометкой «устарели» и текстом ошибки; остальные ноды не страдают. Графики и таймеры «уже N» строятся в браузере по последовательным опросам (около 40 точек на DC, хранятся на время сессии браузера).

**Состояния.**

| Состояние | Значение |
|-----------|----------|
| доступен (up) | Эндпоинты достижимы и нужные ME-райтеры живы (без ME — пробы upstream достают до DC). |
| деградация (degraded) | Живых райтеров меньше требуемого или достижимо менее 50% эндпоинтов DC. Ёмкость снижена, но трафик идёт. |
| недоступен (down) | Нет достижимых эндпоинтов, нет живых райтеров или все здоровые upstream сообщают, что DC недостижим. |
| неизвестно (unknown) | Данных Telemt по этому DC пока нет. |

Состояние всегда показывается иконкой и текстом, а не только цветом.

**Поля.** RTT — время отклика Middle-End (или лучшая задержка подключения upstream, если у ME значения нет); *Эндпоинты* — достижимые/всего ME-эндпоинтов; *ME-райтеры* — живые/требуемые соединения-райтеры, *Покрытие* — их отношение; *Сессии* — клиентские сессии на этом DC; *IP-семейство* — IPv4/IPv6/оба/недостижим по пробам upstream; *Источник* — берётся ли состояние из пула Middle-End или из проб upstream. Идентификаторы: `DC1`-`DC5` — основные дата-центры, `DCn media` (отрицательные id в Telemt) — медиа-дата-центры, `DC203 CDN` — кластер CDN. В раскрытом DC также видны пол райтеров (мин/цель/макс), эндпоинты с числом райтеров, идущие восстановления и достижимость через upstream; в деталях инстанса — пул ME-райтеров, счётчики переподключений и потерь маршрутов и здоровье каждого маршрута upstream.

**Вид подстраивается под размер плитки.** Маленькая плитка — одна строка сводки и цветные точки DC; средняя — чипы по DC; большая — таблица со спарклайнами RTT. Содержимое прокручивается внутри плитки.

**Работа с виджетом.** В шапке — общее здоровье (все доступны / N деградировали / N недоступны), счётчики по панели и нодам, возраст последнего обновления с индикатором свежести, кнопки обновления и паузы, интервал опроса, опциональное (включается вручную) уведомление браузера при переходе DC из доступного в недоступный и кнопки копирования диагностики (текст или JSON) для поддержки. Фильтры: только проблемы, нода, поиск по тегу/названию/имени ноды; сортировка по проблемам, RTT или сессиям; группировка по нодам или по DC. DC, чьё состояние изменилось с прошлого опроса, коротко подсвечиваются, а список **События** хранит последние 20 переходов.

**Недоступные инстансы** показывают код причины и подсказку: `api_disabled` (включите `server.api.enabled` в параметрах Telemt), `feature_disabled` (установите `server.api.minimal_runtime_enabled = true`), `unreachable` (проверьте, что адрес прослушивания API включён, инбаунд запущен и в логе нет ошибок), `source_unavailable` (у Telemt ещё нет снимка; подождите после перезапуска).

## Пользовательские панели дашборда: доступные метрики

Панели типа «метрика» выбирают данные из каталога с поиском. Группы: ресурсы панели, сеть, клиенты, ноды (сводка), «Нода: <имя>», балансировщики (сводка), «Балансировщик: <имя>», Telemt, трафик, база данных, процесс панели. Сохранённые панели ссылаются на метрики по id, поэтому id не меняются.

- **Сводки.** `nodes.*` и `balancers.*` объединяют все включённые ноды или балансировщики: `nodes.cpu.avg|max|min`, `nodes.mem.avg|max`, `nodes.disk.avg|max`, `nodes.latency.avg|max`, `nodes.traffic.up|down|total`, `nodes.rate.up|down` (байт/с за последние 5 минут), `nodes.clients.online`, `nodes.offline`, `balancers.connections`, `balancers.healthy`, `balancers.pools.unhealthy` (бэкенды, помеченные как недоступные), `balancers.rate.in|out`, `balancers.errors`, `balancers.failovers` и другие.
- **По сущностям.** Каждая нода и каждый балансировщик выбираются по имени: `node:<id>:cpu`, `node:<id>:traffic.down`, `node:<id>:status`, `balancer:<id>:connections`, `balancer:<id>:healthy`. Подпись: «<имя> · <метрика>». Если ноду или балансировщик удалили (или пропал доступ), панель показывает «нет данных», а редактор отмечает метрику как недоступную.
- **Счётчики панели.** `stats.clients.*`, `stats.inbounds.*`, `traffic.up|down|total`, `traffic.rate.up|down`, `audit.events24h|failed24h` (счётчики аудита требуют `audit:read`).
- **Источник.** `GET /panel/api/server/dashboardMetrics` (право `dashboard:read`; данные нод дополнительно требуют `nodes:read`, балансировщиков `balancers:read`). Ответ кэшируется на сервере примерно 8 секунд, строится только сгруппированными запросами и не обращается к нодам и агентам: значения берутся из последней проверки и опроса ресурсов. Для ноды или балансировщика не в сети живые значения (CPU, соединения и т. п.) равны null, суммарный трафик остаётся.
- **Единицы и пороги.** Значения форматируются по единице (байты, байт/с, проценты, мс, число, длительность, статус). У метрик есть пороги предупреждения и критичности как метаданные (CPU 70/90 %, память и диск 80/90 %, задержка 150/500 мс, доля рабочих бэкендов ниже 99/50 %).
- **Шаблоны.** «Обзор нод» (карточка на ноду: статус, CPU, память, трафик, клиенты онлайн) и «Обзор балансировщиков» (статус, соединения, рабочие бэкенды, пропускная способность, ошибки).
