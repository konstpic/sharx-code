# 14. Балансировщики

[← Пакеты](./13-pakety.md) | [Оглавление](./README.md)

## Что такое балансировщик

**Балансировщик (Balancer)** — отдельный сервер с **HAProxy** или **nginx (stream)** перед нодами. Клиент подключается к адресу балансировщика, а тот передаёт соединение на одну из нод, где работает тот же инбаунд.

```
клиент ──► балансировщик:ПОРТ ──(TCP/UDP насквозь)──► нода:порт инбаунда ──► Xray
```

Трафик **не расшифровывается**, поэтому Reality, TLS, VLESS, VMess, Trojan, Shadowsocks, Telemt и остальные протоколы работают без изменений; в ссылке клиента меняется только адрес.

Что это даёт: один стабильный адрес для нескольких нод, автоматическое исключение упавшей ноды, распределение нагрузки, скрытие IP нод от клиентов.

Раздел находится в меню **Ноды → Балансировщики** (`/panel/nodes/balancers/`) и, как и **Ноды**, доступен в режиме Multi-Node.

## Составные части

| Часть | Описание |
|-------|----------|
| **Агент** | Процесс на вашем сервере: принимает конфигурацию от панели, проверяет её движком (`haproxy -c` / `nginx -t`), подменяет атомарно и перезагружает без обрыва текущих соединений. Если проверка не прошла, работает прежний конфиг, а ошибка видна в панели. После перезапуска сам поднимает последнюю применённую конфигурацию. |
| **Пул** | Один инбаунд, «поставленный за балансировщик»: порт, распределение, проверка здоровья, PROXY protocol, участники. |
| **Участники пула** | Ноды пула: вес, «резерв», включена ли нода. По умолчанию берутся из назначенных инбаунду (опция «Следовать нодам инбаунда автоматически»). |

## Движки

| | HAProxy | nginx (stream) |
|---|---------|----------------|
| TCP | да | да |
| UDP (Hysteria2, WireGuard, AmneziaWG) | нет | да |
| Проверки здоровья | активные (TCP connect каждые 3 с) | пассивные (два отказа подряд, пауза 10 с) |
| Распределение | «По кругу», «Наименьшее число соединений», «По IP клиента (закрепление)» | те же |

UDP-инбаунд можно поставить только за балансировщик с движком **nginx** — панель это проверяет.

## Добавление и установка

1. **Ноды → Балансировщики → Добавить балансировщик**: **Название**, **Публичный адрес (куда подключаются клиенты)**, **Движок**, при необходимости **Адрес API агента** (по умолчанию `http://<публичный адрес>:8080`) и **Заметка**.
2. Нажмите **Установить на сервер** и выберите способ:
   - **Автоматически по SSH.** Укажите **SSH-хост**, **Порт**, **Пользователя** и **Пароль** либо **Приватный ключ**. Нажмите **Проверить сервер и установить**. Панель прочитает **отпечаток SSH-ключа** сервера и попросит подтвердить его («Подтвердите отпечаток SSH-ключа сервера»): сравните с выводом `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` на сервере и нажмите **Отпечаток совпадает, подключиться**. Без подтверждения соединение не открывается. Затем панель поставит Docker (если его нет), запишет `docker-compose.yml` в `/opt/sharxbalancer`, запустит агента и отправит конфигурацию. Учётные данные используются один раз и не сохраняются.
   - **Вручную (docker-compose).** В окне установки готовый `docker-compose.yml` с вашим `SECRET_KEY`. Сохраните на сервере и выполните `docker compose up -d`.
3. В файрволе сервера откройте **порт агента** (по умолчанию **8080**) для панели и **порты пулов** для клиентов. Агент работает в `network_mode: host`.

Канал панель — агент защищён JWT с общим секретом, но **без TLS**: ограничьте порт агента адресом панели.

## Пулы

**Балансировщики** → у карточки **Поставить инбаунд за балансировщик**:

| Поле | Описание |
|------|----------|
| **Инбаунд** | Какой инбаунд балансируется (UDP — только на nginx) |
| **Порт балансировщика** | Порт для клиентов; пусто — «как у инбаунда» |
| **Распределение** | По кругу / Наименьшее число соединений / По IP клиента |
| **Что получит клиент в подписке** | Показывать ли балансировщик (см. ниже) |
| **Ноды в пуле**, **Вес**, «резерв» | Участники; при «Следовать нодам инбаунда автоматически» набор нод ведётся сам |
| **Вес участника** | Как определяется вес каждой ноды: Вручную, Авто: по нагрузке ноды, Авто: по пингу (см. ниже) |
| **Исключать ноды, которые перестали отвечать** | Проверки здоровья |
| **PROXY protocol** | Реальный IP клиента на нодах (см. «Ограничения») |
| **Пул включён** | Включение пула |

Панель отправляет конфигурацию агенту и сверяет её каждые 15 секунд: смена нод инбаунда, порта, отключение ноды подхватываются сами. Кнопки на карточке: **Обновить статус**, **Отправить конфигурацию**.

## Вес участника: Вручную, Авто: по нагрузке ноды, Авто: по пингу

По умолчанию HAProxy/nginx просто распределяют соединения по кругу (или по выбранному алгоритму), считая всех участников равными по весу. **Вес участника** в форме пула меняет то, как определяется вес каждой ноды:

| Режим | Откуда берётся вес | Нода без данных |
|-------|----------------------|-------------------|
| **Вручную** | Число, которое вы вписали в столбец **Вес** для каждой ноды | — (вы всегда задаёте его сами) |
| **Авто: по нагрузке ноды** | Заданная админом **Пропускная способность (Mbps)** ноды (Ноды → редактировать) против её реальной отдаваемой нагрузки | Уходит в низкий вес по умолчанию (1) вместо полного исключения |
| **Авто: по пингу** | TCP-задержка, которую сам агент балансировщика измеряет до этой ноды | Недоступная нода, или та, о которой агент ещё не отчитался, уходит в низкий вес по умолчанию (1) |

Для **«Авто: по нагрузке ноды»** нужна одна дополнительная настройка на каждой ноде: откройте **Ноды → редактировать ноду → Пропускная способность (Mbps)** и укажите реальную ширину канала ноды (0 = неизвестно). Node-сервис снимает показания с основного сетевого интерфейса каждые 3 секунды и отдаёт текущую нагрузку панели; панель превращает `нагрузка / пропускная способность` в процент загрузки и даёт больший вес нодам с запасом. Нода, у которой оставлено 0 Mbps, не исключается — она просто всегда получает низкий вес по умолчанию, то есть всё равно получает часть трафика в этом режиме.

Для **«Авто: по пингу»** ничего дополнительно настраивать на стороне ноды не нужно: агент балансировщика и так делает TCP-подключение к каждому участнику пула в рамках своей проверки здоровья, и теперь замеряет время этого подключения. Более близкие/быстрые ноды (меньшая задержка до балансировщика) автоматически получают больший вес. Этот режим стоит использовать, когда важнее не загрузка, а физическая/сетевая близость к балансировщику — например, если клиенты обычно подключаются через балансировщик в конкретном регионе и вы хотите, чтобы он предпочитал ближайшую ноду.

Оба авто-режима пересчитываются по общему таймеру — **Настройки → Общие → Автовес балансировщика → Интервал пересчёта (сек)** (по умолчанию 30 с, минимум 5 с — одна настройка, применяется ко всем пулам в авто-режиме). Каждый пересчёт записывает новый вес в строки участников пула и заново отправляет конфигурацию агенту, так что `docker exec ... cat haproxy.cfg` на балансировщике покажет текущие расчётные веса (`server sN <host>:<port> weight <N> ...`).

Переключение пула на **Вручную** останавливает пересчёт для этого пула; последние расчётные (или заданные вами) веса остаются, пока вы их не измените.

> Авто-вес выбирает только *сколько* трафика получает здоровая нода — он не заменяет проверки здоровья. Нода, не прошедшая проверку здоровья, всё равно исключается из ротации независимо от режима веса.

## График трафика

Кнопка **Трафик** на карточке балансировщика открывает живой график: скорость «К клиентам» и «От клиентов», число соединений, разбивка по пулам. Данные снимает агент каждые 2 секунды, история за последний час хранится в агенте, БД панели не нагружается. У nginx нет счётчиков по портам, поэтому показана оценка (половина сетевого трафика сервера).

## Как балансировщик попадает в подписку (модель 2.0)

Если у пула включена выдача в подписке, панель создаёт хост «Балансировщик» (`pool`); он появляется в разделе **Хосты** сам. Клиент получит его только если хост **включён в пакет** ([Пакеты](./13-pakety.md)). Порядок записей в подписке задаёт порядок хостов в пакете:

| Хотите | Что положить в пакет |
|--------|----------------------|
| Балансировщик, затем прямые ноды как запас | хост балансировщика, затем хосты нод |
| Прямые ноды, балансировщик последним | хосты нод, затем хост балансировщика |
| Только балансировщик | только хост балансировщика (адреса нод скрыты; если балансировщик недоступен, маршрута нет) |
| Балансировщик работает, но в подписке его нет | пул без выдачи в подписку («Не показывать балансировщик») или хост не включён в пакеты |

Несколько балансировщиков на один инбаунд поддерживаются.

> **До версии 2.0** режим выдачи («балансировщик, затем прямые», «прямые, затем балансировщик», «только балансировщик») выбирался на пуле и определял порядок сам. В 2.0 порядок задаёт пакет; при обновлении прежние режимы пулов пересчитываются в порядок хостов пакетов, а конвертация проверяет, что подписки не изменились. В форме пула выбор режима сохранился; для порядка в подписке ориентируйтесь на пакет.

## Ограничения

- **IP клиента.** Без PROXY protocol ноды видят адрес балансировщика: лимиты по IP, сессии и география на нодах показывают его. PROXY protocol включается на пуле, но инбаунд должен принимать его (`acceptProxyProtocol`); прямые подключения к этому порту тогда перестают работать. Используйте вместе со схемой «только балансировщик».
- **Здоровье.** Проверка на уровне L4 видит лишь «порт принимает соединения». Нода с зависшим Xray и открытым портом остаётся в ротации.
- **Точка отказа.** Один балансировщик — одна точка входа. Оставляйте в пакете и прямые ноды после хоста балансировщика, либо используйте два балансировщика.
- **Без терминации TLS.** WebSocket/gRPC за CDN, где нужен TLS на балансировщике, не поддерживаются: для них используйте [адресный хост](./06-hosty.md) и CDN.
- Канал панель — агент без TLS (см. выше).
